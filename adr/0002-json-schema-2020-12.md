# ADR-0002: JSON Schema 2020-12 and `$defs`

**Status:** Accepted
**Date:** 2026-08-21

## Context

The schemas were authored against JSON Schema draft-07, published in 2018.
Three limitations of that draft block work the project needs to do.

**Renames have no transition path.** Correcting `flouride` to `fluoride` (#214)
or settling the `pH`/`ph` split (#208, currently 3 properties spelled `pH`
against 8 spelled `ph`) means either breaking every existing file or carrying
the misspelling forever. draft-07 has no `deprecated` keyword, so there is no way
to publish the correct spelling while keeping the old one valid. This was
identified on #214 as the reason that fix has not shipped.

**`allOf` types cannot reject unknown keys.** In draft-07,
`additionalProperties` only sees properties declared in the same schema object.
Placed next to an `allOf`, it rejects everything the other branch contributes:

```
draft-07, additionalProperties: false on CultureAdditionType
  valid document -> REJECTED: must NOT have additional properties {"additionalProperty":"name"}
```

This is why 20 of the format's object types omit `additionalProperties`
entirely, and it means every `*AdditionType`, `*Information` and `WaterType`
silently accepts any misspelled key. The gap is not theoretical: enabling
`unevaluatedProperties: false` on those types rejects **59 distinct keys already
present in this repository's own test corpus**, including the whole of
`recipe.style` as emitted by the bundled BeerXML converter, nine properties that
`generic/recipes.json` puts on hop additions, and 38 keys in the BJCP and
Brewers Association style guides under `tests/styles/` (among them Spanish and
Portuguese translations of the BJCP 2021 text). None of that was detectable
before.

**Descriptions next to `$ref` are ignored.** draft-07 specifies that a `$ref`
causes sibling keywords to be ignored. These schemas pair `$ref` with
`description` in many places; those descriptions reach the generated
documentation but no validator ever sees them.

## Decision

The format moves to JSON Schema 2020-12
(`https://json-schema.org/draft/2020-12/schema`), and `definitions` is renamed
to `$defs` with every `$ref` pointer updated to match.

`$id` values are also corrected to point at `main` rather than the renamed
`master` branch.

`unevaluatedProperties: false` is **not** enabled by this decision. It is what
makes the migration worth doing, but turning it on is a separate change that has
to land with fixes for the 59 keys it rejects, and some of those are open format
questions rather than bugs. The keyword is now available; adopting it per type
is future work.

## Alternatives considered

**Stay on draft-07.** Maximises compatibility with older validator libraries,
which is a real concern for a format implemented largely by hobby software. It
was rejected because it permanently forecloses both the rename path and unknown
key detection, and because the compatibility argument has weakened: 2020-12 is
what OpenAPI 3.1 uses, which pulled broad support into every major validator
ecosystem.

**Migrate to 2019-09.** Provides both `deprecated` and
`unevaluatedProperties`, so it would solve the immediate problems. Rejected
because it is a way station: 2020-12 is the current draft and has wider library
support, precisely because of OpenAPI 3.1.

**Keep `definitions` under 2020-12.** `definitions` still works as an ordinary
JSON Pointer target, so this would have been a zero-churn option and was
seriously considered. Rejected in favour of being idiomatic: `$defs` is the
keyword for the draft the format now declares, and a schema that declares
2020-12 while using the draft-07 keyword invites exactly the kind of
"is this deliberate?" question ADR-0001 exists to prevent. The cost is
acknowledged below.

**Version the `$id` URLs** (for example `.../schema/1.0/hop.json`) so consumers
can pin. This is a real problem: `$id` currently points at a moving branch, so
its meaning changes with every merge. It is out of scope here and needs its own
decision.

## Consequences

- **Easier:** property renames can ship with a deprecation period; `allOf`
  types can be closed to unknown keys; descriptions adjacent to `$ref` become
  meaningful; `const`, `dependentSchemas` and the rest of the modern vocabulary
  become available.
- **Harder:** consumers need a validator that supports 2020-12. In practice
  this means a recent version of the library they already use, but it is not
  nothing for software pinned to an old dependency.
- **Breaking:** any consumer that string-matches `#/definitions/` rather than
  resolving pointers properly will not find the types. A consumer that resolves
  `$ref` correctly is unaffected. Nothing changes for BeerJSON _documents_: all
  46 test documents validate unchanged, and ajv reports no strict-mode issues
  against the migrated schemas.
